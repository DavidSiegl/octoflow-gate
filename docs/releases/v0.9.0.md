# The gate runs Go's tools

A Go project gets what a Rust one does: its tests and their coverage judged, its code linted, and the functions a
change edits mutation-tested.
[docs/quality-gate.md](https://github.com/DavidSiegl/octoflow-gate/blob/main/docs/quality-gate.md) says how each
works.

- **golangci-lint** is a linter of the gate, run in each Go module whose `go.mod` git tracks (one under `testdata` or
  `vendor` aside) with the module's own configuration, every finding asked for; its findings on added lines fail the
  gate, as clippy's do, and code that does not compile is a failed condition naming the type checker's first error.
  `[linters] golangci-lint = [...]` in `gate.toml` chooses its files, `go.mod` among them, and `[]` turns it off.
- **Tests and coverage**: a `[[test]]` command that runs
  `gotestsum --junitfile junit-go.xml -- -coverprofile=coverage-go.out ./...` gives the gate the failing Go tests,
  through the JUnit reader it has, and the coverage of new code: a Go coverage profile is a coverage report beside Cobertura and LCOV, from a command or
  `--coverage`, its files named by their packages' import paths and read back through each module's `go.mod`.
- **Surviving mutants**: gremlins mutation-tests the Go functions a change adds lines to or removes lines from, whole,
  within the one `--mutation-budget`, which mutmut, cargo-mutants and gremlins now share in turn; the findings are
  mutmut's kinds, `untested` for mutants on lines no test runs.

A change to Go may now fail the gate where it passed under 0.8.0: a golangci-lint finding on an added line, a module
that does not compile, or, through a `[[test]]` command, a failing Go test or coverage below 80% of 20 or more new
lines. go, golangci-lint and gremlins come from `PATH`, and a project that tracks Go files and lacks golangci-lint
fails the gate naming it, until it installs it or sets `[linters] golangci-lint = []`.

Go's tests are not rerun for flakiness, nor run at the base.
